### トピック3: recorder / reminiscence / digest の役割評価

**整理した各ツールの役割：**

**recorder（minutes/）：**
- 稼働条件：手動トリガー（「記録して」等の指示）
- 出力形式：構造化された議事録（決定事項・未解決課題を明確化）
- 読者：人間（プロデューサー、チーム成員）
- Claude の活用：能動的に参照（新規課題診断時に過去決定との整合性確認）
- ファイル保存先：`minutes/[日時]_[議題].md`

**reminiscence：**
- 稼働条件：自動（全セッション時刻をログ、Q&A を蓄積）
- 出力形式：生 Q&A ログの時系列蓄積（構造化なし）
- 読者：主に Claude（キーワード inject で自動補完）
- 役割：「過去のセッション断片」を prompt 時に自動注入、文脈の補完

**digest（現状）：**
- 稼働条件：週次自動実行（W12-14 などの週単位生成）
- 出力形式：週単位の Q&A ダンプ（生ログのまま）
- 読者：人間が読むこともあるが、主に Claude の参照用
- **判明した問題**：「構造化ダイジェスト」と呼んでいるが、実態は raw Q&A の週まとめに過ぎない。minutes のような「決定事項抽出」は行っていない。

**抽出された課題：**
- digest の「真の構造化」（決定事項→action→結果の抽出）には LLM による処理が必要
- 従量課金 API は採用しない方針のため、現状の自動化では限界あり
- minutes と digest が「役割の棲み分け」を明確にして、互いに補完する設計が必要

**決定事項：**
- digest の構造化レベルは「現状維持」（生 Q&A 週まとめ）
  - 将来的に推論能力を持つ自社 Claude インスタンスが実装されれば改善の余地あり
- minutes/ の役割は「人間向けアーカイブ + Claude が能動的に読む補完資料」として明確化
  - 決定事項をメタデータ付きで記録
  - 未解決課題の所有者・期限を明記
  - 「なぜそう決まったか」の文脈を保持
- recorder の空白期間は reminiscence inject で自然に補完される仕様
  - 明示的な「運用ルール化」はしない（自動補完の仕組みで十分）
- 各ツールの役割分担を `docs/_index.md` と CLAUDE.md に明記

**次のアクション：**
- `docs/_index.md` に「minutes / digest / reminiscence の役割分担図」を追加
- CLAUDE.md の「セッション管理ルール」に digest・reminiscence の参照タイミングを記載

### トピック4: CLAUDE.md ルール変更（context-watch 警告時の対応）

**変更内容：**

**変更前（2026-04-09 確定版）：**
```
context-watch 警告が出たとき（20ターン以上）：
- 現在のトピックが完了していれば recorder を即呼ぶ
- 完了していない場合はユーザーに「記録してから続けますか？」と確認する
```

**変更後（2026-04-11 決定）：**
```
context-watch 警告が出たとき（20ターン以上）：
- 確認なしで即座に recorder を呼ぶ
- 未完了のトピックでも「その時点まで」を記録する
- 記録後、続行するか新セッション開始するかをユーザーに確認
```

**変更の理由：**
- 警告が出ている時点で、ユーザーに確認を取ること自体が token を消費
- recorder への記録は「未完了」「進行中」「一時中断」なども正確に記録でき、損失がない
- 先制的に記録することで、context reset 時に最小限の情報喪失で済む
- token 効率とセッション連続性の両立

**CLAUDE.md への修正箇所：**
- セッション管理ルール → context-watch 警告時の項目を上記に修正

**次のアクション：**
- CLAUDE.md を修正（確定）
