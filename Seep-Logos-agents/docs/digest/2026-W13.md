## 記事の要旨：CoDD（Coherence-Driven Development）

### AIエンジニアリングの3段階進化

| フェーズ | 時期 | 内容 |
|---|---|---|
| プロンプトエンジニアリング | 2023-2024 | 1回のやり取りを最適化（Few-shot等） |

### 未解決だった問題

ハーネスまで進化しても残る問題 → **「仕様変更時、影響がどこまで波及するかを人間が追い続けなければならない」**。大規模プロジェクトでこれは破綻する。

### CoDDの解法（`pip install codd-dev`）

- Markdownのフロントマターで設計書間の**依存関係を宣言**
- `codd impact` コマンドで変更の**波及範囲を自動特定**
- Green/Amber/Grayの3段階で**信頼度付きで影響分類**

設計書をAIが生成 → 人間は要件と制約だけ入力 → 変更があっても依存グラフが瞬時に影響範囲を返す、という流れ。

## 調査結果のサマリー

### YAML vs JSON：差は限定的

| 観点 | YAML | JSON |
|---|---|---|
| トークン効率 | 約18%少ない（引用符・カンマ不要） | 冗長だがミニファイで削減可 |
| LLMの読取精度 | インデントミスで構文エラーのリスク | 構造が明確で解析エラーが少ない |
| 人間の可読性 | 高い（コメント書ける） | やや低い |
| Claudeとの相性 | Anthropic自身がYAMLフロントマター採用 | structured outputsで公式サポート |

**結論：どちらでも大差ない。** 選択基準は「外部ツール（jq等）と連携するか（→JSON）」か「人間が直接読み書きするか（→YAML）」。

### ファイルベース vs プロンプト直接渡し：ここは差が大きい

| 観点 | ファイルベース | プロンプト直接渡し |

Q: dispatcherが必要となるリスクは？
A: 4つあります。

---

**1. `--dangerously-skip-permissions` による権限無制限実行**

dispatcherが起動するサブプロセスは全ツールを無制限で使えます。誤った指示が渡されると、意図しないファイル操作やコマンド実行が止まりません。

---

**2. 多重起動**

同じYAMLファイルに短時間で複数回 Write が起きると、dispatcher が複数回発火して同じエージェントを二重・三重に起動します。現状はそれを防ぐ排他制御がありません。

---

**3. エラーが見えない**

起動したプロセスは `/tmp/seep-web-*.log` に記録するだけでバックグラウンドで動きます。失敗しても司令塔には通知されず、YAMLが中途半端な状態で放置される可能性があります。

---

**4. 状態不整合**

プロセスが途中でクラッシュすると YAML の status が `in_progress` のまま止まります。次回 dispatcher が発火したとき「pending ではない」と判定されて起動をスキップし、**詰まったまま進めなくなります**。

---

3. 「このシナリオ稿・このLP原稿・このアート指示書が影響を受けます」と出力される
4. 確認が必要なものは人間がレビュー、自動更新できるものはAIが更新

ドキュメントの整合性を手動で追いかける作業をなくすのが目的です。

Q: CoDD入れるとトークン消費激しくなるかな？
A: CoDD自体はトークンを**減らす方向**に働く可能性が高いです。

## 理由

**CoDD導入で増えるもの**
- 各ファイルのフロントマター（`depends_on` 宣言）→ 数行/ファイル、軽微
- `codd impact <file>` の出力をコンテキストに渡すとき → 数十〜数百行

**CoDD導入で減るもの**
- 依存関係を手動でトレースするために複数ファイルを順番に読む処理
- 「CLAUDE.mdを変えたらどこに波及するか」を自力で追う多段Read → これが現状のボトルネック

## 判断

```
現状: Read(CLAUDE.md) → Read(docs/*.md) → Read(agents/*.md) → ... [多段、合計コスト大]
CoDD: codd impact CLAUDE.md → 影響リストだけ返す [1回のBash実行 + 出力]
```

skill化すれば「`codd impact` の出力だけ受け取って必要なファイルだけ読む」という流れになるため、**全体としてトークンは節約できる見込み**です。

## 注意点

依存グラフが大きくなりすぎると `codd impact` の出力自体が重くなるので、宣言する依存関係は**直接依存のみ**に絞る設計が重要です（推移的依存は自動展開に任せる）。

Q: ブレークポイント定義ってなに？
A: 画面サイズによってレイアウトを切り替える**境界値**のことです。

例：

```css
/* モバイル: 〜767px → 1カラム、フォント小さめ */
@media (max-width: 767px) { ... }

/* タブレット: 768〜1023px → 2カラム */
@media (min-width: 768px) and (max-width: 1023px) { ... }

/* PC: 1024px〜 → フルレイアウト */
@media (min-width: 1024px) { ... }
```

DESIGN.md にこれを書いておくと、AIが「スマホで見たときはこうする」という判断を自分でできるようになります。
